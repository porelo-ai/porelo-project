# PJ105 — An Issue Carries Its Data In A JSON Head

```json
{
  "$schema": "issue-1.json",
  "id": "PJ105",
  "title": "An Issue Carries Its Data In A JSON Head",
  "state": "Implementing",
  "size": "M",
  "priority": "Medium",
  "rank": 1,
  "blockedBy": [],
  "covers": "Every issue carries its data in a JSON head checked by one shared schema, each index is generated from the heads, and tools read the heads instead of Markdown tables."
}
```

**Why this size.** the tooling in porelo-buildtools is BT46's pattern for issues (M); each repository's conversion is one command and a commit (XS each).

Stories already have their head (BT46, in Review), which [PJ104](README.md#pj104) waited for.

**What must be true.** Every issue in every repository of the project carries its data - number, title, state, size,
what it is blocked by, the one line its index shows - in a JSON head at the top of its own file, checked by one JSON
schema shared by all repositories. Each repository's `issues/README.md` is generated from those heads. Tools across
repositories read the heads, never a Markdown table. The prose below the head stays Markdown, written by hand.

## Why

Today an issue's data stands twice: in its file's first lines and in a row of its repository's index, kept in step by
hand. Tools that need it - the plan pages and `plan check` in porelo-buildtools, the coordinator's state table, a
story's derived state ([PJ104](README.md#pj104)), and later the coordinator through Porelo's MCP server
([PJ103](README.md#pj103)) - parse Markdown tables. One machine-readable place per issue, checked by a schema, serves
every tool alike and leaves nothing to drift.

## Decided by the operator (2026-11-08)

- **Mixed form:** data in a head, prose in Markdown, one file per issue; the index is generated, not the issue's prose.
- **The head is JSON**, checked by a JSON schema.
- **Stories come first** in this form ([PJ104](README.md#pj104), porelo-buildtools BT46); the issues of all repositories
  follow as this issue.

## The shape proposed

- A JSON object at the top of each issue file, set apart from the prose; the exact fencing is decided with
  porelo-buildtools.
- The schema, the generator of the index and the check that the index equals the generation live in
  porelo-buildtools and run in every repository's document checks.
- The shared block of `AGENTS.md` says how an issue's head is written, who sets which field, and that the index is
  never edited by hand.
- The existing issues are converted by a script from their first lines and their index rows; a difference between the
  two is listed for the repository's agent, not guessed.

## Acceptance

- In every repository, `issues/README.md` equals what the generator makes from the heads, and the document checks
  refuse a hand-edited index.
- An issue whose head fails the schema is refused by the document checks, naming the field.
- The plan pages and the coordinator's state table read issues from the heads alone.

## Plan

Decided here so the parts can start at once; the operator changes any of it in the room.

**The head.** Right below the title line, a fenced block opened by ```` ```json ```` and closed by ```` ``` ````, so
the forge shows it as code above the prose. One object, checked by `issue-1.json`, held in porelo-buildtools beside
`story-2.json`:
- `$schema` (`"issue-1.json"`), `id`, `title`, `state` (a state of `issues/workflow.yml`), `size` (`XS`..`XL` or
  `-`), `priority` (`Highest`..`Lowest`, default `Medium`), `blockedBy` (ids of the same repository), `covers` (the
  index line);
- optional: `parent` and `role` for a sub-issue (BT56's form), `severity`, `kind`, `openQuestions` (a count).

The `**Status:**`, `**Size:**`, `**Blocked by:**` and `**Priority:**` lines leave the prose; every other line stays as
written. A state's reason (who set it, when) stays a prose sentence below the head.

**The index.** `issues/README.md` is generated by `porelo-release issues index` from the heads: one table per state in
the workflow's order, rows ordered by `priority`, then by `rank`, a number the conversion
writes from the old index's order and an agent changes to move a row. The intro, the
"What was decided along the way" part and Rejected's rows (whose files are gone) are kept from the file: Rejected rows
stay as rows of their own, since their issue has no head any more.

**The check.** `porelo-release issues check` in the document checks: every head by the schema, the index equal to its
generation, every `blockedBy` known. A hand-edited index is refused naming the first differing line.

**The conversion.** `porelo-release issues convert` once per repository: reads each file's lines and its index row,
writes the head, and stops listing every difference between the two (state, size, blocked by, the line) for the
repository's agent instead of guessing. Run again after the fixes, it writes and leaves nothing to do.

**The parts.**
1. porelo-buildtools (Agent Machines), one BT issue, M: schema, `issues index`, `issues check`, `issues convert`;
   the stories library (`IssueIndexes`) reads heads where a file has one, the index rows else, so the planner and
   `stories check` work through the change; the shared block's rule text ("an issue's data stands in its head; the
   index is never edited by hand"), the workflows' document checks call `issues check`; docs and changelog.
2. Every repository with an index (19 today, porelo-planner included), its own agent, XS each: once the snapshot
   is published, run `issues convert`, mend what it lists, run `issues index`, commit, Push ready. porelo-buildtools
   first, as the proof; then all others in one gathered round.
3. The coordinator: `stand.py` and the story table read heads; the shared block's new hash to every repository.
